What sets this apart

Most locator tooling falls into one of two camps: a manual point-and-click inspector that hands you whatever the DOM happened to look like at that instant, or a "self-healing" layer that quietly rewrites your selectors later and hides how often it's actually guessing. This takes a different position — verify before you ever see it, keep re-verifying for as long as you keep working, and say exactly why a locator is trustworthy or not instead of just handing one over.

Inspect — the hover tooltip

the chain: hover → resolve against the live DOM → grade the result → show every copyable form

Every element gets escalated through the same ladder a careful engineer would use by hand — test hook, then role + accessible name, then label/placeholder, then a scoped chain for duplicate rows, then CSS as a last resort — and stops at the first one verified unique against the live page. A heatmap and CSV export cover the whole page at once, not one element at a time.

Two Playwright lines? Pick by where your test starts

When the element you're hovering lives inside a module embedded from a different origin, you can get two Playwright forms, not one. They end in the identical chain — the prefix is the whole difference, and the tooltip highlights it:

test opens that module's URL directly page.locator('…') — your spec navigates straight to that module
test starts at the app shell page.frameLocator('iframe[src*="…"]').locator('…') — your spec logs in and navigates into the module from there

Get this wrong and the locator returns 0 matches with no error explaining why: page.locator() cannot see inside a frame. That single mistake is the most common reason a "correct" locator appears broken.

While you're actually recording, only one of these shows. Mid-recording, the tool already knows which one your test needs — there's a real page.goto() into this exact origin sitting in the script by then, either from starting the recording there or from the cross-origin handoff described under Record — so there's nothing left to guess. Outside a recording (just hovering to grab a locator for a test you're writing by hand) both stay shown, because there the tool has no way to know which one your target test actually uses.

Read the verdict, not a letter grade

SHIP IT

Pinned on a test hook, or on role + accessible name. Put it in a test.

WORKS — WATCH IT

Resolves 1-of-1 today, but pinned on markup or wording. It breaks when either changes, and the tooltip says which.

DON'T SHIP

Not unique, purely positional, or a third-party widget rather than your app.

Underneath sits a needs row — what the test has to do, a separate question from whether the locator is good. A perfect locator can still need one: open-container (it's in a collapsed menu — the tooltip hands you the click that reveals it), needs-framelocator, click-wrapper, not-clickable, pierces-shadow, third-party-widget.

Cross-checking the CSS in DevTools

Alt+C, then Cmd+F in the Elements panel, paste. The tooltip already told you the number you'll get — measured against shadow boundaries, cross-origin iframes, and page-text substring matches, the same three things that make DevTools search harder than querySelectorAll.

Health — watches what you actually rely on

the chain: touch it (hover, copy, or record) → tracked → re-checked only when the real page changes → toast the instant it breaks

Hovering, copying, or recording a click on something adds it to a watch list. A background observer re-checks every watched locator whenever the app's own DOM actually changes — switching this tool's own tabs, or one of its own toasts appearing, is filtered out and never triggers a wasted re-check. Only real page changes count.

Ambiguous means it was 1-of-1 and now matches several — the one failure that makes a passing test click the wrong thing. You get a toast the moment it happens, not just a number buried in a tab you have to remember to check. Off-page just means the element isn't on the pages visited since — that's a fact about your browsing, not a defect in the locator, and it's tracked separately so it never gets confused with an actual break.

Record — turns using the app into a test

the chain: Start recording → every click/fill/select/check/press becomes a verified step → cross-origin hop auto-detected → hand off, resume, keep going → Stop → export

Every action gets the SAME 1-of-1 verified locator Inspect would give you, not a raw positional selector — and the best one wins if a field's grade improves mid-flow (an autocomplete opening, say), rather than locking in whatever was available on the very first keystroke. Undo drops the last step, Redo brings it back, Clear starts over. Export as a flat Generic script or a Page-Object-style Company script — same recording, two shapes.

One thing that will confuse you

Some modules load in a cross-origin iframe

No bookmarklet can reach inside one — that's a browser rule, not a gap in this tool. Click it on the shell and you get the shell: nav, launcher, panels, banners, toasts. To inspect or record inside that module, open it in its own tab and click the bookmark there — or use the amber banner's Record in X instead button, which opens the new tab, carries everything recorded so far into it automatically, and resumes recording the instant you click the bookmark there once. That one click can't be skipped: a script can't inject itself into a tab it has no handle to.

Either route, the locators come back already wrapped in the right frameLocator(...) call when your test starts at the shell — nothing for you to add by hand, and nothing recorded silently: recording from the shell while working inside the module would otherwise skip those steps with no error and no gap marker, so the Record tab warns you before you press the button, every time.

Recorded a flow? Two edits before you run it

test('TODO rename: ...')       →  give it a real name
const data = { step3: '...' }  →  your test data, hoisted in one place
// ASSERT (enable + edit):     →  uncomment and fill in

The recorder captures what you did, never what you were checking. A recording with no assertions passes as long as nothing crashes — that's a script, not a test.

Landing on the login wall on replay? Add await page.pause() after the page.goto(...): the run opens a real browser and waits, you log in by hand, hit Resume, and the rest executes.

Learn — the memory that carries over

the chain: quietly accumulate good locators as you browse → copy one → promoted to Approved → recalled instantly next time → cleaned up on your terms, never silently

Every locator this tool derives is quietly measured against a quality bar — a URN, a real test hook, role + accessible name — never a positional guess — and the good ones accumulate locally in this browser, across sessions, without you doing anything. Copy one on purpose (Alt+P, an alternative row, however) and it's promoted to Approved: the next time you're back on that exact element, it's recalled instantly instead of re-derived.

Approved something by mistake? Remove that one — no need to wipe everything you've ever learned for this site. Clear stale only ever touches entries that are both unused for 30+ days and low-confidence — a URN pin from three months ago, or anything you've reconfirmed more than once, survives regardless of age. This report is also what you hand a developer: which data-testid values this build actually defines versus which have rendered in your session so far.

Doctor — "this locator isn't working, why?"

the chain: paste, or let it auto-populate → every segment run against the live page → the exact point it stops matching → verified alternatives, one click to copy

Paste a failing locator, press Check this locator, and every segment is run against the live page so you can see the exact point it stops matching. Three input forms are accepted and it detects which is which:

Playwright chainpage.getByRole('button', { name: 'Save' })
plain CSS selector[data-row-key="urn:li:…"] button — paste the Alt+C line straight back in
XPath//button[contains(text(),'Save')]

The headline answers one question — does it find the element? matches 1 is a pass even when that element happens to be hidden or unclickable right now; those are reported separately underneath, because they're facts about the page, not the locator. Check it on the screen where it's meant to work — a locator for a dialog reads as "finds nothing" while the dialog is closed, and that's the correct answer.

You don't always have to paste anything. Anything you copied or used in a recording that later goes ambiguous shows up automatically at the top of this tab as "Needs checkup" — click it to run the diagnosis immediately, or dismiss it if it's not worth chasing right now. Locators you only ever hovered — never copied or recorded — don't clutter this list; Health still tracks those, this tab is just the ones you actually relied on.

Feed — every toast, caught the instant it appears

the chain: a message renders → captured immediately, even sub-second ones → matched to the API call that fired moments earlier → one entry, not two things to correlate by hand

Toasts, banners, and validation messages get caught the moment they appear, not on a polling interval that misses the ones that vanish fast. Each one is linked to the network or GraphQL call that triggered it, so an error message and its cause show up together — you're not left cross-referencing a timestamp against a separate network tab by eye.

Why a bookmarklet, and what it never does

Extensions need IT approval and are blocked outright in managed browsers like Island. This is a link in your bookmarks bar — no install, no permissions prompt, no policy exception, and it works the same way on every page of the app, not just the one it happened to be built against.

Nothing leaves the browser. Captured URLs are redacted to host + path with id-like segments masked plus the GraphQL operation name; no request or response bodies are ever read. The recorder masks password, card and OTP fields. What it learns is stored in local IndexedDB and Learn → Clear all stored data erases it. Every DOM and network hook is wrapped so a bug in this tool cannot throw into the app's console, block navigation, or break its requests.
